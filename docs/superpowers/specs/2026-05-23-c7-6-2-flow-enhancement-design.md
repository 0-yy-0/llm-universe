# C7 6.2《流程增强》教学重构设计

**日期**：2026-05-23  
**范围**：`notebook/C7 高级 RAG 技巧/6. 增强阶段/2. 流程增强.ipynb`  
**关联文件**：`notebook/C7 高级 RAG 技巧/6. 增强阶段/4. 选型总结.md`、`notebook/C7 高级 RAG 技巧/6. 增强阶段/_common.py`  
**前置背景**：`docs/superpowers/specs/2026-04-18-c7-enhancement-stage-redesign.md`、`docs/superpowers/plans/2026-05-10-c7-6-2-flow-question-design.md`

## 1. 背景与问题

当前 `6.2 流程增强` 已经实现了多种方法，但教学主线仍不够聚焦，主要问题不是“方法太少”，而是“方法之间的关系、边界与增益条件没有被稳定讲清楚”。

从学习者视角看，当前版本存在以下风险：

1. **章节焦点容易漂移**：读者能看到多个高级方法名，但不一定明白这一节究竟在讲“什么变了”。本节真正变化的是 **RAG 的控制流**，而不是 query 改写、上下文拼接或系统级 agent。
2. **方法关系不够清晰**：`iterative retrieval`、`recursive decomposition`、`query routing`、`adaptive retrieval`、`CRAG`、`Self-RAG` 各自都能读懂一点，但缺少统一框架，学习者不容易建立“它们分别在流程的哪个决策点介入”的整体认知。
3. **重复内容稀释主线**：与第 4 章 query/document 对齐、6.1 上下文增强、6.3 系统增强的边界虽有提及，但尚未成为章节开头的清晰导航；读者容易把跨章节概念混在一起。
4. **评估叙事容易被误读为排行榜**：当前结果容易让人盯住最终分数，却忽视 trace、题型匹配和方法适用条件。对流程增强来说，单纯追求“均值谁更高”不是最好的教学组织方式。
5. **局部表述存在误导风险**：例如迭代与递归的对比若不够准确，会直接影响学习者对方法差异的理解。

因此，本次重构的核心不是新增 runnable 方法，而是将现有 6 个方法重组为一条清晰的“流程决策主线”，并把重复内容抽象、跨章节内容边界化、评估结果机制化。

## 2. 目标与非目标

### 2.1 目标

1. **把本节主线统一为“RAG 控制流如何被改造”**，让学习者一眼看出本节和第 4 章、6.1、6.3 的区别。
2. **保留并强化现有 6 个方法**，不弱化 `iterative retrieval`、`recursive decomposition`、`query routing` 这些本章核心方法的地位。
3. **把重复铺垫抽象掉**，让每个方法的展示只聚焦本方法新增的决策点与失败模式。
4. **把评估重心从“静态排行榜”改为“整体趋势 + 匹配题型上的可解释提升”**，同一套评估运行同时产出主评估表与方法级 targeted/case panel，避免选择性报告。
5. **让学习者能从 trace、case study、题型差异中理解增益来源**，而不是只读一个最终分数。

### 2.2 非目标

- **不新增第 7 个 runnable 方法**。本轮不把章节扩展成“方法清单大全”。
- **不重复实现第 4 章已覆盖的方法**，例如 query/document 对齐类方法只在边界处引用，不在本节展开重复代码。
- **不把 6.3 的系统级方法前移到 6.2**，避免单次请求内流程与跨请求、多文档、多源工具或状态化系统能力混淆。
- **不追求开放域 benchmark 或 SOTA 排名**。本节仍以教学可复现、机制清楚为优先。
- **不承诺所有方法在所有题上都优于 baseline**。本节要展示的是“何时有效、为何有效、何时无效”。

## 3. 核心设计原则

### 3.1 主线优先于方法名堆叠

章节不再以“列出多个高级 RAG 方法”为组织方式，而是围绕一个统一问题展开：

> 当基础 RAG 的一次检索、一次生成不足时，如何通过控制流改造来补证据、拆复杂问题、选择策略、过滤噪声并自我检查？

### 3.2 本节只讲“单次请求内的流程决策”

四层边界在本节开头明确说明：

- **第 4 章**：query/document 对齐，关注“问题如何更容易被检索到”。
- **6.1**：上下文增强，关注“检索结果如何组织得更利于生成”。
- **6.2**：流程增强，关注“单次请求内何时再检索、拆解、路由、纠错、自评”。
- **6.3**：系统增强，关注“跨请求、多源、工具化、记忆和代理系统能力”。

这一段要作为读者进入本节时的导航，而不是散落在后文的补充说明。

其中 `query routing` 的边界要更硬地写清楚：6.2 只讨论 **单次请求内的检索策略或索引配置选择**，例如 chunk 粒度、top-k、数学/概念分支、稠密/关键词检索分支等；不讨论 6.3 范畴内的多文档 agent、工具路由、跨请求记忆或长期状态管理。

### 3.3 重复内容复用，变化点显式暴露

基础检索器、公共评估、通用辅助函数继续复用 `_common.py` 或本节已有公共逻辑；每个方法展示只保留以下内容：

- 新增的决策点
- 新增的 trace 信号
- 针对的失败模式
- 增益与局限

### 3.4 机制证据优先于单个数字

流程增强是否“有效”，不只看最终答案得分，而要同时看：

1. **流程是否在应该触发时触发**
2. **新增或替换的证据是否更合适**
3. **最终答案覆盖是否因此改善**

换言之，本节的“证据”必须来自 **题型 + trace + answer + 评分** 的联合观察。

## 4. 章节结构设计

建议将本节结构重组为以下阅读路径。

### 4.1 本节解决什么问题

开头先建立基础 RAG 的局限：

- 一次检索可能漏证据
- 复杂问题可能需要先拆解
- 不同问题可能适合不同检索策略
- 检索结果可能包含噪声或部分相关证据
- 模型可能在证据不足时过早停止

然后引出本节核心命题：**流程增强不是“找更多资料”，而是“改变资料被获取、筛选、使用的顺序与条件”。**

### 4.2 本节与其他章节的边界

紧接着用一个小节明确：

- 本节不会重复 query/document 对齐方法；
- 本节不会重复上下文组织方法；
- 本节也不会提前进入系统级 agent；
- 本节只关心单次请求内的控制流。

该小节的目标是让读者先知道“本节不讲什么”，从而更容易把注意力留在本节真正的变化点上。

### 4.3 统一观察框架

在进入具体方法前，给出本节统一观察框架。每个方法都用同样的问题来理解：

1. 它改变了 RAG 的哪个流程环节？
2. 它针对什么失败模式？
3. 它什么时候更可能带来增益？
4. 它什么时候可能不值得用？
5. 它的 trace 中应该出现什么信号？

这能显著降低学习者在不同方法之间来回切换的认知成本。

### 4.4 六个方法按“决策点”展开

本节继续保留 6 个方法，但组织上强调它们在控制流中的位置与层级关系：

1. **`iterative retrieval`**：答案草稿暴露缺口后，进入第二轮或后续检索。  
2. **`recursive decomposition`**：生成前先把复杂问题拆成更容易分别检索的子问题。  
3. **`query routing`**：检索前根据问题类型选择不同检索策略或索引配置，例如 chunk 粒度、top-k、数学/概念分支；不扩展为工具路由、多文档 agent 或跨请求状态。  
4. **`adaptive retrieval`**：不只选择索引，而是直接调度不同流程。  
5. **`CRAG`**：检索后先评估证据质量，再决定是否过滤、降级或纠错。  
6. **`Self-RAG`**：生成过程中引入自评，让模型决定是否继续检索或停止。  

这种顺序能把六个方法串成一条“控制流越来越复杂”的连续主线，而不是平铺的六个独立技巧。

### 4.5 横向总结与选型回收

章节末尾不再只给一个静态结果表，而是收回到统一问题：

- 这些方法分别改变了哪个决策点？
- 它们对哪类题更有帮助？
- 哪些方法更像局部修补，哪些方法已经接近“更强的流程编排器”？

这样能自然衔接到 `4. 选型总结.md`，而不是让总结部分与正文脱节。

## 5. 方法展示模板

六个方法都使用统一模板，避免每节都重新发明讲法。

### 5.1 模板结构

每个方法建议按以下 6 段展开：

1. **直觉**  
   用 2~3 句话说明：为什么它属于流程增强，而不是检索前改写或上下文后处理。

2. **流程图**  
   只画本方法新增的决策点，不重复基础 RAG 的所有细节。

3. **适用失败模式**  
   明确说明它针对的失败模式，例如“漏证据”“多跳”“粒度错配”“噪声片段”“过早停止”。

4. **最小实现**  
   代码只展示本方法独有逻辑；公共检索、通用生成、共用评估一律复用。

5. **trace 解读**  
   说明读者应该在 trace 中观察什么，哪些字段代表流程真的被改变了。

6. **增益与局限**  
   用一句话概括“预期增益来自哪里”，再用一句话说明“在哪些情况下它可能没有必要”。

### 5.2 方法级重点

为避免六个方法讲法趋同，每个方法都要强调一个最关键的观察点：

- `iterative retrieval`：是否出现“草稿缺口 → 再检索”的链条。
- `recursive decomposition`：子问题是否真正分担了原问题的不同子任务。
- `query routing`：分支选择是否与问题类型匹配，且分支确实造成检索差异。
- `adaptive retrieval`：调度是否把题目送进更合适的流程，而不只是换个名字。
- `CRAG`：证据质量判断是否真的改变了上下文输入。
- `Self-RAG`：自评是否对“继续/停止/重查”产生了实质影响。

## 6. 评估与数据集设计

### 6.1 数据集策略

本节继续使用当前南瓜书 QA 语料，不替换主数据集。原因有三点：

1. 与整章语境一致，便于教学复现；
2. 概念题、比较题、推导题都存在，足以展示多种流程差异；
3. 读者不必额外下载新 benchmark，即可在已有环境中复现本节实验。

但需要在本节前部补充明确说明：

- 这是 **封闭教材场景**，不是开放域 benchmark；
- `train_dataset.json` 在这里是教程题库，不应被解读为机器学习意义上的训练集/测试集划分；
- 本节评估只用于 6.2 内部横向比较，不和 6.1 直接进行数字横比。

### 6.2 评估目标

评估目标从“谁更高分”调整为：

> 这些流程改造是否在它们本该解决的问题类型上，展示出可解释的增益？

因此，本节评估要在 **同一套评估运行** 中同时保留两层：

1. **主评估表**：继续保留小规模整体题集，用于观察总体趋势；
2. **方法级 targeted/case panel**：每个方法选 2~3 道更适配的方法题，展示机制是否真的起作用。

这两层可以在 notebook 中分开展示，但不能变成两套彼此独立的实验。主评估表和 targeted/case panel 必须同跑、同裁判、同 baseline：同一批方法实现、同一评分逻辑、同一 baseline 对照同时产生整体结果与方法级 case 结果。主表回答“整体趋势如何”，targeted panel 回答“在方法适配题上，机制是否触发、证据是否变好、指标或覆盖是否改善”。不能用口头解释替代 case 证据，也不能只挑选有利结果进行选择性报告。

### 6.3 增益判定标准

每个方法是否“真正带来增益”，至少同时满足以下三项中的两项，最好三项都满足：

1. **流程触发正确**：例如 iterative 出现追加检索、recursive 出现有效拆解、routing 进入合理分支。
2. **证据质量改善**：新增证据更贴近问题，或噪声被过滤，或子问题补齐了缺失角度。
3. **答案覆盖改善**：最终答案比 baseline 补足了关键点、推导步骤或比较维度。

这套标准可以避免把偶然涨分误判为流程型方法的真实收益。

每个方法还必须至少提供 1 个真实可运行 case，能够展示该方法相对 baseline 的具体机制差异。理想情况下，case 同时给出指标提升或答案覆盖改善；如果指标没有提升，也必须通过 trace 定位失败发生在哪个环节，例如没有正确触发、检索分支选错、证据质量未改善、生成阶段未吸收证据等。不能把“没有触发”“没有提升”本身当作合格交付，除非它被明确写成失败 case，并服务于方法边界解释。

### 6.4 结果解释方式

本节最终结果不再写成“固定排行榜式结论”，而应写成“阅读说明”：

- 哪类题更适合某方法；
- 某方法如果没涨，是因为题型不匹配、baseline 已足够、还是流程没有正确触发；
- 为什么 trace 证据比单个均值更重要。

### 6.5 对“指标提升”的定位

本节设计希望看到指标提升，但不把“所有方法均值都涨”作为前提条件。更合理的表述是：

- **主目标**：帮助学习者理解流程增强机制；
- **次目标**：在方法适配的题型上尽量观察到可解释的分数提升；
- **不承诺**：每个方法都在整体均值上优于 baseline。

## 7. 重复内容复用与抽象策略

### 7.1 需要抽象的内容

以下内容应统一复用，避免在六个方法里重复解释：

- 本节的统一实验设置
- trace 数据结构与打印方式
- 统一的“适用 / 不适用 / 增益 / 局限”讲解模板
- 评估免责声明
- baseline 对照说明

### 7.2 需要显式保留在正文的内容

以下内容必须显式保留在每个方法小节中，因为它们构成本节真正的教学重点：

- 方法新增的控制流决策点
- 方法独有的 trace 形状
- 与 baseline 的机制差异
- 方法失败时的边界样例

### 7.3 与其他章节的复用关系

- 第 4 章的方法只做边界说明与引用，不在本节重复实现。
- 6.1 的上下文组织经验可以在本节复用为背景知识，但不再重讲其实现细节。
- 6.3 的系统级能力只作为“本节之外的下一层抽象”点到为止。

## 8. 明确不做的内容

本轮设计明确不做以下事项：

1. 不新增一个新的 runnable 流程方法；
2. 不把本节扩展成 2026 年所有 RAG 流程方法的综述；
3. 不在本节内重新实现第 4 章已有的对齐方法；
4. 不把小样本评估包装成广泛可推广的结论；
5. 不为了“提分更好看”而改动方法核心逻辑，使其偏离教学原型。

## 9. 验收标准

本节重构完成后，应满足以下标准：

1. **章节定位清楚**：学习者读完开头，能明确区分第 4 章、6.1、6.2、6.3 的分工。
2. **主线统一**：六个方法都能被放回同一个“控制流决策点”框架中理解。
3. **重复减少**：每个方法小节不再重复铺垫大量基础设置，而是聚焦方法独有逻辑。
4. **重点突出**：`iterative retrieval`、`recursive decomposition`、`query routing` 被明确呈现为本章主线方法，而不是被边缘化。
5. **评估更可信**：结果展示中同时出现题型、trace、答案差异和得分，不再只给一个静态结论表。
6. **边界更清晰**：本节不再与 query/document 对齐、上下文增强、系统增强混淆。
7. **指标解释合理**：章节明确说明“希望看到适配题型上的提升”，但不承诺所有方法在整体均值上都赢 baseline。
8. **评估同源可追溯**：主评估表和方法级 targeted/case panel 来自同一套评估运行、同一裁判、同一 baseline，可分开展示但不能分开解释成两套证据体系。
9. **方法 case 真实可运行**：6 个方法每个至少有 1 个真实可运行 case，能展示相对 baseline 的机制差异；若指标或覆盖未改善，必须用 trace 定位失败环节，不能把“未触发/未提升”当作合格交付。
