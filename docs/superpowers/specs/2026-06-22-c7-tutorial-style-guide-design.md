# C7 高级 RAG 教程写作规范设计

**日期**：2026-06-22  
**范围**：`notebook/C7 高级 RAG 技巧/` 第二部分高级 RAG 教程，优先覆盖 `6. 增强阶段`，后续可回填到 C7 其他章节  
**关联文件**：`notebook/C7 高级 RAG 技巧/6. 增强阶段/1. 上下文增强.ipynb`、`notebook/C7 高级 RAG 技巧/6. 增强阶段/2. 流程增强.ipynb`、`notebook/C7 高级 RAG 技巧/6. 增强阶段/3. 系统增强.ipynb`、`notebook/C7 高级 RAG 技巧/6. 增强阶段/4. 选型总结.md`

## 1. 背景与目标

当前 C7 高级 RAG 内容已经覆盖了上下文增强、流程增强、系统增强、评估等方向，但历史版本容易出现三个问题：

1. **像方法清单，而不像工程实验课**：读者能看到很多方法名和代码，但不一定知道这些方法分别修复哪类 RAG bad case。
2. **实验主线不够稳定**：有些结论依赖少量案例或局部指标，容易让读者怀疑方法是否真的优于 baseline。
3. **教程颗粒度不均匀**：有的地方重复基础环境和工程细节，有的地方又过度黑盒，读者难以抓住核心机制。

本规范的目标是把 C7 统一成一种更成熟的教程形态：

> 面向已经会基础 RAG 的读者，用可运行实验和 trace 教他们诊断失败、选择增强方法、验证优化效果。

也就是说，C7 不是从零讲 RAG，也不是论文综述，而是一门 **高级 RAG 工程实验课**。

## 2. 目标读者

### 2.1 主读者

主读者是已经能写基础 RAG 的学习者。他们理解切块、embedding、向量检索、top-k、prompt 和基础检索问答链，但遇到效果不好时，不知道如何定位问题、选择优化方法、验证改动是否有效。

### 2.2 副读者

副读者是有一定算法或研究兴趣的读者。他们希望理解 Sentence Window、Small-to-Big、CRAG、Self-RAG、Agentic RAG 等方法的机制位置，但不需要论文级推导。

### 2.3 明确不面向

C7 不再面向完全没有 RAG 经验的读者。基础概念已经由前序章节承担，因此 C7 不应反复解释 embedding、向量数据库、基础检索链等内容。

## 3. 教程定位

C7 的统一定位是：

> 你已经有一个基础 RAG 了，现在我们一起把它调好。

每个章节都应该训练一种诊断能力，而不只是介绍一组方法名。章节主线应从 bad case 出发：

```text
bad case -> baseline trace -> 方法介入 -> 新 trace -> 同题对比 -> 评估 -> 边界总结
```

读者学完 C7.6 后，最核心的能力应是：

> 看到一个 RAG bad case，能判断问题主要出在上下文、流程，还是系统层，并选择一个低成本方法先验证。

## 4. 总体写作风格

### 4.1 实验手册为骨架，短讲义为解释层

Notebook 应以实验推进为主，以短讲义解释关键机制。推荐比例是：

- **70% 实验手册**：代码、trace、同题对比、结果表、失败案例。
- **30% 短讲义**：机制解释、适用边界、方法位置、选型判断。

讲义解释要短，但要有判断力。避免空泛表述，例如“该方法可以提升检索效果”。应改成更具体的机制句：

> Small-to-Big 不负责让 query 匹配得更准，它解决的是“命中了细节，但生成时缺少上层语义”的问题。它用小块做召回，用父块补上下文。

### 4.2 问题驱动，而不是方法驱动

每节开头不应直接说“本节介绍某某方法”，而应先复现基础 RAG 的失败现象。方法出现时，读者应该已经知道它要修复什么问题。

### 4.3 正文负责过渡，表格负责整理

不要一开头就甩大表。更自然的写法是先用自然段引出问题，再用轻量表压缩结构。

示例：

```text
基础 RAG 出问题时，表面现象往往都是“答错了”，但背后的原因并不一样。
有时是检索命中了相关片段，却缺少前后文；有时是一个问题本来就需要多轮检索；
还有些问题不是单次请求能解决的，而是依赖历史、多文档或工具状态。

本章把这些问题按“需要增强的位置”分成三类：
```

然后再接轻量表：

```text
现象 | 主要缺口 | 本章方法
检索命中但上下文不全 | 证据范围太窄 | 上下文增强
一次检索不够 | 流程缺少多步决策 | 流程增强
单次请求不够 | 缺状态、多源或工具编排 | 系统增强
```

## 5. Notebook 统一结构

每个核心 notebook 推荐使用以下结构：

```text
0. 本节要解决什么失败模式
1. 复现 baseline 失败
2. 诊断：失败发生在哪一环
3. 方法 A：最小实现 + trace 对比
4. 方法 B：最小实现 + trace 对比
5. 方法 C：最小实现 + trace 对比
6. 同题横向对比
7. 小规模复现实验
8. 失败与副作用
9. 选型总结
```

其中第 1、2、6、8 节尤其重要。没有 baseline 失败、trace 诊断和失败边界，章节就容易退回方法堆叠。

## 6. 方法小节模板

每个正式方法都应回答五个问题：

```text
它修什么？
它怎么修？
trace 里哪里变了？
结果是否真的更好？
什么时候不该用？
```

建议固定为以下模板：

1. **一句话问题定位**：先说明这个方法修复哪类现象。
2. **机制解释**：说明索引时做什么、检索时做什么、为什么可能改善。
3. **教学最小实现**：保留核心机制代码，避免堆工程细节。
4. **trace 对比**：展示 baseline 与方法在同一题上的证据变化。
5. **评估结果**：展示统一口径下的主分数和本节相关题型表现。
6. **适用 / 不适用**：用短句说明工程边界。
7. **副作用提示**：简短说明可能引入的风险。

### 6.1 标题风格

标题保持与前序章节兼容，采用：

```text
## 英文方法名：中文一句话作用
```

示例：

```text
## Sentence Window：补回邻近上下文
## Small-to-Big：用小块召回父级段落
## AutoMerging：合并多个相邻证据块
## Query Routing：为不同问题选择检索策略
## CRAG：在检索质量不足时纠偏
```

这样目录仍然像方法教程，正文读起来则是诊断实验。

### 6.2 适用 / 不适用

每个方法固定保留短边界模块。不要写成长篇优缺点列表，建议控制在 3 行以内。

示例：

```text
适合：
- 检索已经命中关键句，但答案依赖前后文。
- 文档按句子或段落组织较清晰。

不适合：
- baseline 根本没有命中相关区域。
- 上下文窗口一扩大就引入大量干扰信息。
```

## 7. 代码组织原则

### 7.1 Notebook 正文看机制

Notebook 正文应保留教学最小实现，让读者看懂方法关键动作。复杂工程能力不要淹没正文。

### 7.2 公共工具保运行

路径处理、PDF 加载、embedding 初始化、Chroma 构建、LLM 调用、评估 runner 等公共能力放到 `_common.py` 或本章公共工具文件中。

### 7.3 脚本支撑完整评估

完整评估、断点续跑、批量重跑、结果落盘等放到单独脚本中。Notebook 正文只展示关键结果和必要调用。

### 7.4 复杂方法用教学版手写核心机制

对于 AutoMerging、GraphRAG、Agentic RAG 等经典但复杂的方法，正文优先手写教学版最小实现。工程版库或框架可以在小节末尾轻量说明，但不作为正文主线。

## 8. 评测集与结果原则

### 8.1 C7 使用统一评测集

C7 第二部分应使用一个完整独立的统一评测集文件，而不是每章临时拼一套题。建议文件位置为：

```text
notebook/C7 高级 RAG 技巧/data/c7_eval_set.json
```

这套题集服务整个 C7，而不只属于 C7.6 或 C7.7。

### 8.2 数据来源

统一评测集以南瓜书为主。自然题也好，构造题也好，都必须以南瓜书内容为证据来源。

题目可以人工构造，但必须满足：

- 答案能从南瓜书证据中得到支撑；
- 不凭空引入文档外知识；
- 可以覆盖基础、上下文、流程、生成、系统等不同 RAG failure buckets；
- 构造意图服务教学诊断，而不是为某个方法宣传。

### 8.3 题集字段保持轻量

题集不做 benchmark 式复杂元数据包装。推荐字段：

```json
{
  "id": "c7_ctx_001",
  "question": "...",
  "reference_answer": "...",
  "buckets": ["context", "boundary"],
  "evidence_need": "需要结合命中片段前后的相邻上下文"
}
```

不建议加入 `source` 这类字段，因为它对教程正文帮助有限，且容易显得刻意。

### 8.4 规模与运行方式

第一版统一评测集控制在 **60-80 题**。每章 notebook 默认运行本章相关切片，通常为 **12-20 题**。完整评估由脚本支持。

推荐模式：

```text
提交的 notebook：保留作者运行后的关键输出，打开即可阅读。
默认运行：本章相关切片，用于快速复现和观察 trace。
完整复现：运行全量评估脚本，用于严肃验证。
```

### 8.5 结果展示

正文主表使用一个简单主分数，解释区补少量维度。不要把每节写成评测论文。

推荐主表：

```text
方法 | 全量均分 | 本节相关题均分 | 平均调用次数/耗时
```

推荐评分口径为 0/1/2：

```text
0 = 答错或无依据
1 = 部分正确
2 = 正确且依据充分
```

如果完整结果和本地复现存在轻微波动，应把波动作为 RAG 评估的一部分自然解释：

> RAG 评估有波动，但趋势应可复现。如果单题分数不同，看 trace；如果整体趋势反向，优先排查环境、模型版本、索引状态和评估缓存。

## 9. 指标与 baseline 要求

### 9.1 正式主方法应整体优于 baseline

如果一个方法只在个别案例上优于 baseline，但整体指标弱于 baseline，不应作为正向主方法强讲。它可以降级为补充方法、失败分析或边界讨论。

如果一个经典方法理论上重要，但在当前统一评测口径下只能持平 baseline，也不应硬写成主线收益。更合适的处理是保留机制介绍和局部可解释 case，并明确放入边界或补充讨论。

### 9.2 同时看全量和相关题型

统一评测集下，每章结果应同时关注：

- **全量指标**：防止方法只在局部有效，但整体伤害系统。
- **本章相关题型指标**：说明方法确实修复了本章目标问题。

### 9.3 不强调“定制题集”

正文不要刻意说“这是为本节定制的题集”。更自然的表达是：

> 下面我们用一组覆盖常见 RAG 失败模式的问题，观察不同方法的表现。

内部选题逻辑要清楚，正文表达要自然。

## 10. 失败案例与边界

每个方法都需要短讲副作用；每个章节集中展示 1-2 个失败或副作用案例。

推荐写法：

```text
失败案例：窗口变大后引入干扰，LLM 反而把不相关条件混入答案。
```

失败案例的目的不是削弱方法，而是训练读者的工程判断：

- 方法为什么没修好？
- 副作用发生在哪一步？
- trace 里能否看到原因？
- 下一步应该换方法、调参数，还是回到数据处理/索引/检索阶段？

## 11. 前沿与论文背景

每个方法可以保留一小段“方法来源与前沿位置”，但不要展开论文综述。

示例：

```text
Self-RAG 原论文更完整地引入了反思 token 和训练机制。
本节只保留推理阶段最容易迁移到工程中的“检索质量判断 -> 是否重检索”思想。
```

这能兼顾 C 类读者的机制定位，但不会冲淡实验主线。

## 12. 统一方法选择总表

C7 需要一张统一方法选择总表，把实验结果收束成工程排障决策。主表应按问题现象组织，而不是按方法分类组织。

推荐结构：

```text
观察到的现象 | 可能原因 | 优先看什么 trace | 候选方法 | 成本 | 风险 | 怎么验证
检索命中但答案缺信息 | 上下文范围太窄 | top-k 片段和上下文覆盖 | Sentence Window / Small-to-Big | 低-中 | 引入噪声 | 看 evidence coverage
复杂问题答一半 | 需要拆解或多跳 | 子问题 trace / 迭代 trace | Recursive / Iterative | 中 | 多次 LLM 调用 | 看子问题覆盖
不同类型问题效果波动 | query 类型影响证据策略 | route trace | Routing / Adaptive | 中 | 误路由 | 看分支命中和答案变化
检索质量不稳定 | 召回证据不足或噪声高 | grader / retry trace | CRAG / Self-RAG | 中-高 | 延迟上升 | 看纠偏前后证据
多轮或多文档状态丢失 | 单次请求视角不足 | memory / source trace | Memory / Multi-Document Agent | 中-高 | 状态污染 | 看跨轮和跨源一致性
```

这张表可以放在 `6. 增强阶段/4. 选型总结.md`，并在 C7.7 中升级成评估与回归闭环。

## 13. 明确不做

本规范明确不要求：

- 不把 C7 改成论文 survey；
- 不把每个方法都做成生产级完整框架；
- 不在每节重复基础 RAG 环境和概念；
- 不在正文展开评测缓存、断点续跑、限流重试等工程细节；
- 不用个别漂亮 case 包装方法整体有效；
- 不把评测集设计讲得太刻意，C7.7 之前只自然使用。

## 14. 后续落地顺序

建议后续按以下顺序落地：

1. 先基于本规范重审 `6.1 上下文增强`，确认结构、标题、评估表和失败案例是否达标。
2. 再重审 `6.2 流程增强`，尤其确认 query routing、adaptive、CRAG、Self-RAG 的整体指标与 trace 证据是否能支撑主线。
3. 然后重审 `6.3 系统增强`，统一 Memory、多文档、GraphRAG、Agentic RAG 的系统层边界。
4. 抽取 C7 统一评测集文件，逐步让 C7 其他章节复用。
5. 最后在 C7.7 中完整解释评测集、分桶评估、结果波动、回归验证和质量门禁。

## 15. 验收标准

后续任一 C7 notebook 按本规范重构后，应满足：

1. 开头能自然说明本节修复的 RAG 失败模式；
2. 至少有一个 baseline 失败复现和 trace 诊断；
3. 正文代码优先展示方法核心机制，而不是工程噪声；
4. 正式主方法在统一评测口径下整体优于 baseline；如果只能持平或局部有效，应降级为补充方法或边界讨论；
5. 结果区同时展示全量趋势和本节相关题型趋势；
6. 每个方法有简短适用 / 不适用边界；
7. 每章有集中失败或副作用案例；
8. Notebook 保留关键运行输出，但清理长日志和噪声；
9. 章节结论能回扣 trace、结果和边界，不写漂移数字或空泛结论；
10. 与前序章节风格兼容，但在 C7 中形成更明确的诊断实验课气质。
