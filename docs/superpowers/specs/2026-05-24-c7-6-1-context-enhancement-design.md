# C7 6.1《上下文增强》教学重构设计

**日期**：2026-05-24  
**范围**：`notebook/C7 高级 RAG 技巧/6. 增强阶段/1. 上下文增强.ipynb`  
**关联文件**：`notebook/C7 高级 RAG 技巧/6. 增强阶段/readme.md`、`notebook/C7 高级 RAG 技巧/6. 增强阶段/4. 选型总结.md`、`notebook/C7 高级 RAG 技巧/6. 增强阶段/_context_enhance_utils.py`  
**前置背景**：`docs/superpowers/specs/2026-05-23-c7-6-2-flow-enhancement-design.md`

## 1. 背景与目标

当前 `6.1 上下文增强` 已经具备可运行内容，也已经形成了单一 baseline、三种增强方法与优势样例的基本骨架。但从教学表达上看，仍然存在三个问题：

1. **主问题虽然正确，但主线还不够硬**：读者能看到 `Sentence Window`、`Small-to-Big`、`AutoMerging`，但未必能稳定记住“这一节解决的不是检索命中失败，而是命中了以后，上下文仍然不够完整”。
2. **方法解释与实验观察还不够分层**：当前 notebook 已有结果面板，但“机制解释”和“本轮真实观察”仍然容易混在一起，读者不一定能区分“方法原理”与“这次实验里确实发生了什么”。
3. **结论存在漂移风险**：如果章节总结直接手写固定数字或泛化表述，后续实验改动后容易与正文证据脱节，削弱教程可信度。

因此，本次设计的核心不是新增方法，而是把现有内容重构成一条更稳定的教学主线：

> 当检索已经大致命中时，如何把更适合生成的上下文补回来？

在这一主线下，本节要帮助读者建立三个认知：

1. baseline 的问题不是“完全没检到”，而是“检到了，但上下文不够完整”；
2. 三种方法分别通过不同机制补上下文，而不是简单地“多塞点文本”；
3. 章节结论必须由同一轮实验中的真实 case、真实比较表和真实观察驱动，不能预设某方法一定更强。

## 2. 非目标

本轮设计明确不做以下事情：

- **不把本节改写成检索前优化章节**。query 改写、query/document 对齐仍属于前文或其他章节，不在 6.1 展开。
- **不把本节扩展成流程增强或系统增强**。多轮检索、路由、自反思、agent 编排等继续留在 `2. 流程增强.ipynb` 与 `3. 系统增强.ipynb`。
- **不新增第 4 个 runnable 方法**。本节仍只围绕 `Sentence Window`、`Small-to-Big`、`AutoMerging` 展开。
- **不追求开放域 benchmark 结论**。本节仍是封闭教材场景下的教学实验，不把小规模结果包装成普适结论。
- **不为了制造“更强”结论而修改方法定义**。如果证据不足，应调整实验组织、参数或结论力度，而不是硬写方法整体更优。
- **不承担生产级评估或第 7 章评估职责**。6.1 只保留教程级 0/1/2 粗评，用于解释上下文增强机制，不把小样本粗评分包装成系统评测结论。

## 3. 目标读者与写作定位

### 3.1 目标读者

本节面向两类读者，同时兼顾二者：

1. **有基础的学习者**：已经理解基础 RAG 的“切块-检索-生成”流程，但还不熟悉为什么“命中相关片段”仍可能答不好。
2. **工程实践者**：希望知道在现有 RAG 已经“基本能检到”的前提下，应该优先尝试哪一种轻量增强方式，以及应该看什么证据判断是否值得保留。

### 3.2 写作定位

本节定位是 **教程优先，但关键实验结论必须可信**。

这意味着：

- 叙事顺序优先服务理解，不按论文综述式堆方法；
- 方法解释要足够直觉，让读者看懂“为什么这样补上下文”；
- 但所有结论都必须落在真实实验输出上，不能依赖静态手写数字；
- 对有效范围、失败边界、数据集局限要写清楚，不夸大外推。

## 4. 重构原则

### 4.1 只围绕“上下文补全”组织章节

本节统一回答的问题是：

> 当检索已经拿回大致相关的内容，但生成仍缺定义、条件、前后文或同段支撑时，如何补回更合适的上下文？

因此，三种方法都要回到同一框架里理解：

- `Sentence Window`：补回命中句的局部邻域；
- `Small-to-Big`：保留小块定位能力，但把生成上下文提升到父块；
- `AutoMerging`：当多个证据分散命中同一父块时，按命中密度抬升到更完整父级上下文。

### 4.2 固定单一 baseline

本节只保留 **1 个固定 baseline**，作为三种方法的共同对照。baseline 的职责是建立一个可复现、容易理解的起点，而不是故意做弱。

baseline 设计要求：

- 使用单一、明确、可复现的默认检索配置；
- 三种方法都相对这一 baseline 做比较；
- 主表、方法小结、case panel、文末总结全部引用同一 baseline 口径；
- 不在方法之间切换不同 baseline，以免读者失去参照系。

### 4.3 “机制解释”和“实验观察”必须分开写

每种方法都必须拆成两个稳定部分：

1. **机制解释**：解释这个方法如何补上下文，为什么它仍属于“上下文增强”，而不是“流程增强”。
2. **实验观察**：展示这一方法在当前题集里的真实结果、代表提分 case、边界样例，以及本轮观察到的适用条件。

这样可以避免把“理论上应该有效”误写成“本轮实验已经证明有效”。

### 4.4 结论由证据驱动，不手写漂移数字

本节所有结论都要从前文证据自然收束出来。结论区允许总结趋势，但不能静态手写某个固定分数、固定题号集合或固定“平均更强”表述。

更具体地说：

- 允许根据本轮汇总表动态总结“哪种题更适合哪种方法”；
- 允许引用本轮代表题观察“方法补回了什么”；
- 不允许在 notebook 文末写死一个未来可能过期的数字结论；
- 如果后续实验结果变化，结论应随真实输出同步变化，而不是与正文脱节。

### 4.5 明确章节边界

本节开头必须把三层增强边界说清楚：

- **6.1 上下文增强**：检索已大致命中，但送入生成的上下文还不够完整；
- **6.2 流程增强**：一次流程不够，需要再检索、拆解、路由、纠错或自评；
- **6.3 系统增强**：问题跨轮、跨文档、跨工具或依赖系统状态。

这段边界说明要作为进入 6.1 的导航，而不是散落在方法小节里的补充备注。

## 5. Notebook 目标结构

建议将 `1. 上下文增强.ipynb` 重构为以下阅读路径。

### 5.1 本节解决什么问题

开头先建立一个清晰判断：

- baseline 往往不是完全检不到；
- 真正问题是：命中片段本身太碎、上下支撑句缺失、同段补充信息没带上；
- 因而本节要做的不是“再想办法检更多”，而是“把更适合生成的上下文补回来”。

### 5.2 本节与其他增强层的边界

紧接着用一个短小但明确的小节说明：

- 这节不讲 query 改写；
- 这节不讲多轮流程控制；
- 这节不讲 agent 或系统编排；
- 这节只讲“检索命中后，如何恢复更完整上下文”。

### 5.3 baseline 观察

baseline 需要单独成段，明确两件事：

1. baseline 的固定配置是什么；
2. baseline 的典型不足是什么。

这里的重点不是拉长 baseline 分析，而是为后续三种方法提供统一对照：它们到底各自在补 baseline 的哪一种“上下文缺口”。

### 5.4 三种方法依次展开

方法顺序保持为：

1. **`Sentence Window`**：从句级邻域补起，最直觉、最轻量；
2. **`Small-to-Big`**：从小块命中提升到父块生成，强调“定位准”和“上下文全”的平衡；
3. **`AutoMerging`**：在多个子块共同命中同父时，展示如何按命中密度自动合并。

这个顺序本身应传达“补上下文粒度逐步变大”的递进关系。

### 5.5 横向总结

章节末尾不再只给一个静态结果回顾，而要收束到三个问题：

- 三种方法分别补回了哪一类上下文；
- 它们更适合什么样的证据缺口；
- 在当前题集上，哪些结论是可以由真实观察支撑的，哪些只能写成边界说明。

## 6. 每种方法的统一呈现模板

三种方法统一使用同一模板，降低读者切换成本。

### 6.1 模板结构

每种方法建议按以下 7 段展开：

1. **方法直觉**  
   用 2~3 句话说明：它补的是哪类上下文，为什么仍属于“上下文增强”。

2. **机制解释**  
   明确它在“检索命中后”做了什么补全动作，必要时用小图或简表辅助，但只画新增变化点。

3. **适用缺口**  
   指出它更适合哪类问题，例如“命中句前后说明缺失”“答案依赖同段定义与例子”“多个证据散落在同一父块”。

4. **最小实现**  
   只展示本方法独有逻辑；公共评估、公共显示函数、公共数据装载逻辑继续复用。

5. **实验观察**  
   先展示该方法相对 baseline 的真实整体结果，再展示代表提分 case 和边界样例。

6. **观察解读**  
   明确回答：这次提分是因为补回了什么；如果没有明显收益，原因更像题型不匹配、上下文预算受限，还是方法本身未触发。

7. **方法小结**  
   用 1 段话归纳“什么时候值得试、什么时候不必默认开启”。

### 6.2 每个方法的重点观察点

为了避免三种方法讲法趋同，每个方法都要强调一个最关键观察点：

- `Sentence Window`：命中句左右补回的邻句是否真的构成了解释闭环；
- `Small-to-Big`：父块回填是否补上了 baseline 原本缺失的定义、条件、例子或比较信息；
- `AutoMerging`：多个子块同父命中时，父块抬升是否比保留碎片更利于生成，而不是只带来冗余。

## 7. 实验与证据规范

### 7.1 数据集与适用边界

本节继续使用当前南瓜书 QA 语料，不替换主数据集。原因是：

1. 与整章语境一致，便于教程复现；
2. 当前题型已足以展示“局部邻域缺失”“同段上下文缺失”“同父多证据汇聚”这三类问题；
3. 读者不需要额外准备新 benchmark。

但必须明确写出边界：

- 这是 **封闭教材场景**，不是开放域问答 benchmark；
- 本节结果主要用于 6.1 内部比较，不对外推到所有语料结构；
- 如果某方法在当前题集有效，结论也应写成“在当前数据形态下观察到”，而不是“普遍更优”。

### 7.2 证据组织方式

本节证据至少包含三层，而且三层必须同源：

1. **主对比表**：三种方法与 baseline 的整体结果；
2. **方法级面板**：每种方法相对 baseline 的提分题、边界样例、代表题；
3. **上下文证据**：代表题中 baseline 与方法实际送入生成的上下文差异。

三层证据必须来自同一轮评估运行、同一 baseline、同一评分逻辑，不能人为拆成两套相互独立的叙事。

进入 implementation plan 时，必须先显式写出本节实验协议，再拆 notebook 修改任务。实验协议至少包含：

- baseline 配置，包括切块、检索器、top-k、生成输入组织与评分入口；
- 题集版本，包括题目来源、题目数量、题目增删规则和固定方式；
- 评分口径，包括 0/1/2 粗评定义、人工或自动评分流程、tie 的判定方式；
- 随机性控制，包括随机种子、模型温度、重跑次数或固定输出策略；
- 上下文预算，包括最大输入长度、截断规则、窗口大小、父块大小和层级回填限制；
- 方法参数，包括 `Sentence Window` 的窗口、`Small-to-Big` 的子块/父块参数、`AutoMerging` 的 top-k、父块层级和合并阈值；
- 可调整参数清单，包括哪些参数允许在合理范围内为寻找真实提分 case 调整，哪些参数一经协议确定不得按结果反向修改。

这份协议的作用是约束实验入口：可以在合理范围内调参以获得更清晰的教学样例，但不能选择性挑题、反向筛题或通过改变方法定义制造提分。

### 7.3 结果解读规范

解读结果时必须遵守以下规则：

- 不把单次分数上涨直接等同于方法机制成立；
- 至少同时观察“上下文是否更完整”和“答案覆盖是否更好”；
- 对回退样例要解释原因，不能只展示提分题；
- 若方法没有在某题上提分，也不能直接判定方法无效，需要先判断是否题型不匹配或预算受限。
- 主表应展示 win/tie/loss 或均值变化等整体信号，不能只用代表 case 支撑整体趋势。
- 6.1 的 0/1/2 粗评只服务教程解释；不要手抄小样本数字到总结中，也不要替代生产级评估或第 7 章的系统评估。

### 7.4 文末总结规范

文末总结必须由前文真实输出驱动，不能手写漂移数字。

推荐总结方式：

- 总结三种方法分别补哪类上下文；
- 总结当前题集上观察到的适用条件；
- 总结哪些方法更轻量、哪些方法更依赖文档层级；
- 明确哪些结论只对当前实验成立。

不推荐的写法：

- 直接写死固定分数或固定排名；
- 用一句话断言某方法“整体最强”但正文没有证据支撑；
- 忽略失败样例，只保留正面观察。

## 8. 关于“提分 case”和“整体强于 baseline”的设计要求与边界

这是本次设计中需要明确写严的一点。

### 8.1 提分 case 是优先验收要求，但必须有失败路径

每种方法应优先至少展示 **1 个真实提分 case**，并满足以下条件：

1. 该 case 来自真实评估运行，而不是手工挑选的演示伪例；
2. 需要能同时看到 baseline 与方法的上下文差异；
3. 需要能解释“为什么这道题更适合这个方法”；
4. 若同一方法存在多个提分题，可只展开其中一个最有代表性的 case，但其余结果仍要在面板中可追溯。

换言之，本节不能只有“理论上应该更好”的方法介绍，而没有真实提分案例。但这条要求不能被理解为可以为了提分而选择性挑题或过度调参。

如果某方法在预设题集和实验协议允许的合理参数范围内仍找不到真实提分 case，应按以下失败路径处理：

1. 透明记录尝试过的合理参数范围、未提分原因和观察到的边界；
2. 不按结果反向删除题目、不替换题集、不改动方法定义来制造提分；
3. 暂停确认，或经用户确认后收紧该方法展示，把它写成“本轮未观察到稳定提分，但可解释其机制和适用边界”；
4. 在方法面板和文末总结中同步收紧结论，避免读者误以为该方法已在本轮实验中得到正向验证。

### 8.2 “整体强于 baseline”是优先目标，不是预设事实

本节设计应把“在当前数据集上整体不弱于 baseline，且最好强于 baseline”写成 **优先目标 / 验收方向**，而不是未经验证的既定事实。

严格表述要求如下：

- **可以写**：实现阶段应优先争取让方法在当前题集上的整体结果不低于 baseline，并尽量做到整体更强；
- **可以写**：如果初版结果不理想，应先检查参数、上下文预算、代表题选择和结果呈现是否合理；
- **必须写**：若最终证据仍不足以支持“整体强于 baseline”，则结论必须收紧为“在特定题型/特定 case 上更有优势”，不能硬写整体更强；
- **必须写**：主表应给出 win/tie/loss 或均值变化等整体证据，整体趋势不能只靠代表 case 支撑；
- **不能写**：某方法整体优于 baseline，这是既定事实；
- **不能写**：即使结果没有支撑，也在总结中保留“整体更强”的静态表述。
- **不能做**：为获得整体更强而改动方法定义、按结果反向筛题、隐藏回退样例或把边界样例从主表中剔除。

### 8.3 验收时对这条要求的落地方式

实现阶段应按以下顺序处理：

1. 先按实验协议为每种方法寻找真实提分 case，并优先确保每种方法至少有 1 个可解释的真实提分 case；
2. 再优先争取让各方法在当前题集上的整体结果达到“不低于 baseline，最好更强”；
3. 若个别方法整体结果仍不理想，应优先调整实现细节、参数和展示组织；
4. 若经过合理调整后，仍无法让某方法稳定支持“整体更强”，则保留提分 case 与边界说明，并在总结中明确收紧外推；
5. 若某方法连真实提分 case 也无法在合理范围内找到，则按 8.1 的失败路径透明记录，并在用户确认后收紧该方法展示。

这样既响应“最好整体更强”的目标，也不越过证据边界。

## 9. 预期产出

本轮 6.1 重构完成后，预期产出包括：

1. 一个主线更清晰的 `1. 上下文增强.ipynb`；
2. 一个固定、统一、可复现的 baseline 对照；
3. 三个按统一模板组织的方法小节；
4. 每种方法优先至少 1 个真实提分 case；若无法满足，则有透明的失败记录和收紧后的展示结论；
5. 与 case 对应的上下文差异展示；
6. 一个由真实输出驱动、不过度外推的章节总结；
7. 一份在 implementation plan 中显式写出的实验协议；
8. 仅保留必要落盘结果，避免为展示而生成冗余文件。

## 10. 验收标准

本节重构完成后，应满足以下标准：

1. **章节定位清楚**：学习者读完开头，能区分 6.1、6.2、6.3 分别解决什么问题。
2. **baseline 唯一且稳定**：全文只有 1 个 baseline，三种方法都围绕它比较。
3. **主线统一**：三种方法都被放回“检索已命中，但上下文不完整”这一核心问题中解释。
4. **机制解释与实验观察分离**：每种方法都能明显区分“原理”与“本轮真实结果”。
5. **提分 case 处理严谨**：三种方法优先各至少 1 个真实提分 case，可回看上下文差异与分数变化；若无法满足，应按失败路径透明记录并收紧结论。
6. **结果可信**：提分题、边界样例、主对比表和上下文展示来自同一轮评估运行。
7. **总结不漂移**：文末总结不写死静态数字，能够随真实输出变化而调整。
8. **边界不夸大**：文中明确说明数据集和场景边界，不把当前结果外推成普适规律。
9. **整体结果表述严谨**：把“整体强于 baseline”写成优先目标或验收方向，而不是默认事实；若证据不足，能收紧结论。
10. **失败路径明确**：若某方法在预设题集和合理参数内找不到真实提分 case，应透明记录原因，暂停确认或经用户确认后收紧展示，不能选择性挑题或过度调参。
11. **实验协议前置**：implementation plan 必须显式写出 baseline、题集版本、评分口径、随机性控制、上下文预算、top-k/窗口/父块参数，以及允许调整的参数范围。
12. **整体证据完整**：主表展示 win/tie/loss 或均值变化，不隐藏回退样例，不用单个代表 case 替代整体趋势。
13. **粗评边界清楚**：6.1 只保留同一份 0/1/2 教程粗评，不手抄小样本数字，不承担生产级评估或第 7 章评估职责。
