# 处理信息缺口

复杂问题的缺口不只发生在“第一次检索之后”：有些要在索引时保留长文语境，有些要在检索前拆题，有些要根据首轮证据补查，还有些来自对话历史或资料范围。先判断动作发生在哪个阶段，再选择方法。

## 按执行阶段选择方法

| 执行阶段 | 典型缺口 | 对应方法 |
|---|---|---|
| 索引时 | 短片段向量丢失长文语境 | [Late Chunking：长文先整体编码再分块](长文先整体编码再分块.ipynb) |
| 检索前 | 一个问题包含多个独立目标 | [按固定步骤拆分复杂问题](按固定步骤拆分复杂问题.ipynb)、[让模型自动拆成子问题](让模型自动拆成子问题.ipynb) |
| 检索后 | 命中片段缺上下文，或首轮证据不完整 | [句子/父子片段](按句子和父子片段补充上下文.ipynb)、[相邻页面](找到相关页面后补上相邻内容.ipynb)、[有界补查](一次没找全时如何补查.ipynb)、[CRAG/Self-RAG](检查检索结果后再继续.ipynb)、[Agentic RAG](让系统决定怎样检索.ipynb) |
| 会话与来源 | 追问省略对象、范围不清、需要跨来源或关系多跳 | [补全追问](补全追问信息.ipynb)、[资料路由与 GraphRAG](让系统选择资料来源.ipynb)、[多轮多来源助手](构建多轮多来源助手.ipynb) |

单次 query rewrite 和 MultiQuery 仍然回答同一个目标；decomposition 才把多个独立目标拆开。三者的具体边界见 C7 第 4 章的[改写检索问题](../4.%20检索阶段/改写检索问题.ipynb)。

## 索引时保留长文语境

[长文先整体编码再分块](长文先整体编码再分块.ipynb)介绍 Late Chunking：编码器先看到较长上下文，再为短片段生成向量。因此它改变的是检索前的索引向量，不是命中来源后的上下文扩展；本页从“信息缺口”角度解释它，与 C7 第 3 章的[索引方法导航](../3.%20索引阶段/README.md)交叉衔接。

## 检索前拆解问题

1. [按固定步骤拆分复杂问题](按固定步骤拆分复杂问题.ipynb)：先确认问题是否真的含多个独立目标，再按固定结构拆分。
2. [让模型自动拆成子问题](让模型自动拆成子问题.ipynb)：由模型生成子问题，分别检索并保留原问题的方向、条件和先后关系。

拆题发生在第一次检索之前。每个子目标需要独立记录证据覆盖，最后还要检查是否漏掉条件；不要把同一意图的多种说法误当成多个子问题。

## 检索后补回与补查

1. [按句子和父子片段补充上下文](按句子和父子片段补充上下文.ipynb)：比较 Sentence Window、Small-to-Big 和 AutoMerging。
2. [找到相关页面后补上相邻内容](找到相关页面后补上相邻内容.ipynb)：定位连续推导中的一页后，再补回前后页。
3. [一次没找全时如何补查](一次没找全时如何补查.ipynb)：根据首轮结果中明确缺少的内容只补查必要部分。
4. [检查检索结果后再继续](检查检索结果后再继续.ipynb)：用 CRAG 和 Self-RAG 判断证据是否足够，以及是否需要修正检索。
5. [Agentic RAG：用 Agent 编排多步检索](让系统决定怎样检索.ipynb)：实现受约束的 `Plan → Act → Observe → Reflect/Repair → Answer` 闭环，在关键词、向量和混合检索之间选择，并保存逐步 trace。

Agentic RAG 与 Self-RAG 的结构化模型输出必须通过字段、类型、数量和 evidence 绑定检查；非法响应直接失败，不使用重试、备用模型或默认答案。CRAG 使用本地 `BAAI/bge-reranker-base`，准备命令和每种方法的完整运行契约见对应 Notebook；维护检查见[维护说明](../docs/维护说明.md)。

## 对话与资料范围

1. [补全追问信息](补全追问信息.ipynb)：上一轮对象明确时补全检索问题；历史不足或指代不唯一时先澄清，新会话不继承旧历史。
2. [让系统选择资料来源](让系统选择资料来源.ipynb)：主题或章节明确时先缩小南瓜书范围。页末的 GraphRAG 扩展用绑定原文 evidence 的最小关系图演示实体消歧、受限多跳与路径回溯；这些教学关系边不是自动抽取或全库效果证明。
3. [构建多轮多来源助手](构建多轮多来源助手.ipynb)：读取 `data/dataset/manifest.json`、`2. 数据处理/README.md` 和 `7. 评估/README.md` 三份当前项目文件，串起追问补全、真实来源路由、各源独立检索、证据合并、引用绑定、冲突/不足处理和会话边界。

多来源实验只保留本会话最近三轮的必要状态，明确换主题时清空历史。需要生成的页面只从项目根目录 `.env` 读取 `ZHIPUAI_API_KEY`，固定调用 `glm-4-flash`；解析失败或引用无法绑定时直接失败。自动闸门验证结构、来源范围和局部形式支持，不等同于全文人工语义核验、权限治理或生产评测。

## 怎样判断实验结果

每个 Notebook 固定自己的问题、候选语料、检索预算和检查指标，记录补回了什么、增加多少检索，以及改善、持平、退化或不适用的全部结果。不同专题的范围不同，局部成功不能外推到整个资料库。需要同题索引比较时看[C7 第 3 章可选实验](../3.%20索引阶段/比较索引增强方法.ipynb)，需要复查一般问题时看[评估](../7.%20评估/README.md)。

## 实践任务：做一次有界补查或澄清

选一个自己的多条件问题，先运行一次基础检索并明确写出“已找到什么、还缺什么”。只允许进行一次有理由的补查（或在历史不足、指代不明时先澄清），再把两轮结果按稳定 ID 合并；不要把多轮调用当作必然提升。

### 自检标准

- trace 保存原问题、缺口判断、补查 query、每轮的 `source/page/quote` 和停止理由；补查不能只是重复原 query。
- 最终回答的每条 claim 都绑定真实 evidence；没有足够证据时状态为 `insufficient`/`clarify`，不补写外部知识。
- 能指出本次流程增加的检索次数和成本，并用一个原本可回答的问题做回归检查；任一项缺失就退回第 7 章补记录。
