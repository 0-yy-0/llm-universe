# 高级 RAG

本章沿着一条问题驱动的主线学习高级 RAG：先用固定版本的《南瓜书》定位资料、检索和回答中的错误，再逐步处理分块、索引、检索、生成和评估。章节中的核心 Notebook 共享同一份 canonical 数据包，不再维护第二套问题事实来源。

## 从哪里开始

先读[为什么基础 RAG 还会答错](1.%20背景/为什么基础%20RAG%20还会答错.ipynb)，然后按下面的七步主线阅读；遇到具体问题时，可从章节表直接进入对应 Notebook。

| 章节 | 主要内容 |
|---|---|
| [1. 背景](1.%20背景/README.md) | 判断错误来自资料、检索还是回答 |
| [2. 数据处理](2.%20数据处理/README.md) | 读取资料、清理文本、选择分块与向量模型 |
| [3. 索引阶段](3.%20索引阶段/README.md) | 保存资料属性、补充片段背景、结合关键词与向量 |
| [4. 检索阶段](4.%20检索阶段/README.md) | 筛选资料、改写问题、拆题和判断是否继续检索 |
| [5. 生成阶段（检索后处理与回答约束）](5.%20生成阶段/README.md) | 排序、压缩、标注来源，资料不足时拒答 |
| [6. 处理信息缺口](6.%20处理信息缺口/README.md) | 补回上下文、多次检索、追问补全和来源路由 |

## 七步主线

1. [定位错误](1.%20背景/为什么基础%20RAG%20还会答错.ipynb)：区分资料、检索和回答问题。
2. [处理资料与分块](2.%20数据处理/分块优化.ipynb)：确认边界，再选择分块方式。
3. [建立索引](3.%20索引阶段/向量库和资料属性.ipynb)：保存正文、来源和页码等属性。
4. [改进检索](4.%20检索阶段/改写检索问题.ipynb)：在定位问题后改写、筛选或补查。
5. [整理并约束回答](5.%20生成阶段/排序、压缩与回答.ipynb)：引用原文，资料不足时拒答。
6. [处理信息缺口](6.%20处理信息缺口/README.md)：需要多处资料、追问或多来源时补查并保持范围。
7. [评估与收口](7.%20评估/README.md)：先看 C3 method-fit 适配案例，再做 C7 一般回归护栏，最后按协议验收端到端流程。

南瓜书是主线的单文档资料。`data/dataset/` 是唯一的 canonical 问题、证据、qrels 和会话包；`common/dataset.py` 提供严格加载与契约校验。向量库和 PDF 的来源、许可及校验信息见 [`data/README.md`](data/README.md)。

## 先看适配收益，再看一般回归护栏

索引增强的证据分成两层，不能混成一个“方法排行榜”。先看 [C3 可选横向实验](3.%20索引阶段/比较索引增强方法.ipynb)：在同一批 3 道问题、同一组 9 页候选语料、同一 `top_k` 和检索预算下，它展示目标任务适配时的作用——可靠章节标题（CCH）让“机器学习算法有没有绝对更好”这道题的必要页首条排名由 3 提到 2，Document Augmentation 让“集成多个弱学习器”这道题由 2 提到 1；这些是检索排名改善，不是答案质量结论。再看 [C7 评估](7.%20评估/README.md) 中的 6 题 general regression guard：它只检查加入 CCH 后一般问题有没有被伤害，当前两题退化必须保留，不能包装成 CCH 正向演示。

两层证据回答不同问题：C3 问“方法是否适配它要解决的问法”，C7 问“改动是否伤害一般问题”。C7 的退化不抹去 C3 的适配性证据，也不等于教程无用；它提醒读者按资料、问法和预算选择机制，并在发布前同时做适配案例审计与回归检查。

## 三个完整可选实验

三个实验都可在主线之外单独运行；它们复用 canonical 契约，并将真实输入、输出和检查结果保存在 Notebook 中。

1. [C2：数据构建与真实嵌入微调](2.%20数据处理/什么时候需要微调向量模型.ipynb)：用 query→原文 evidence 构建训练/验证范围，保存并重载模型，重新编码后比较训练前后。缺少依赖、模型或数据时直接报错，不替换为伪造结果。
2. [C3：索引增强同题比较](3.%20索引阶段/比较索引增强方法.ipynb)：在同一问题、同一 top-k 和检索字段字符预算下比较原文与索引增强字段，并将命中映回原文核查来源；本实验不组装或比较回答上下文。
3. [多轮多来源助手](6.%20处理信息缺口/构建多轮多来源助手.ipynb)：直接读取 `data/dataset/manifest.json`、`2. 数据处理/README.md` 和 `7. 评估/README.md` 三个当前项目文件，演示追问补全、真实来源路由、各源独立检索、证据合并、引用绑定、冲突/不足处理和会话边界。

## 评估导航与证据边界

评估问题集从[canonical manifest](data/dataset/manifest.json)及其 JSONL 记录加载；冻结 test、训练候选和 regression 的用途由 manifest 与 split 契约区分。三种验证的边界如下：

**问法分布边界**：canonical 数据包保留 163 条 query→evidence pair（101 train、28 dev、34 frozen test），分别覆盖 55、14、17 个互不重叠的 PDF 页面。它们由 `glm-4-flash` 生成和初审，再经独立模型语义复核；110 条二次复核剔除记录及理由单独留档，全部保留记录均为 `human_verified=false`。这些问法是合成数据而不是自然独立用户样本，因此教程结论只适用于这组有限分布，不能外推为自然用户集覆盖。真实 C2 微调在 34 条 frozen test 上逐题为 9 条改善、3 条退化、22 条不变。

1. **C3 method-fit 审计**：[比较索引增强方法](3.%20索引阶段/比较索引增强方法.ipynb)用 3 道适配题观察 CCH、Document Augmentation 等索引字段在目标问法上的作用；候选语料和预算固定在该专题内，不外推为全库效果。
2. **C7 general regression guard**：[比较改动前后](7.%20评估/比较改动前后.ipynb)只比较 bm25 与 bm25_cch 两种检索排序，在同一批 6 道 canonical 回归问题、`top_k` 和上下文预算上计算 Recall@4/MRR。它是副作用检查，不代表 CCH 正向收益，也不代表章节中所有专题方法的统一效果；逐题退化必须保留。
3. **端到端 capstone**：[端到端验收 Notebook](7.%20评估/端到端验收.ipynb)按[验收协议](7.%20评估/端到端验收协议.md)用少量 canonical 固定回归问题（evidence 已按固定流程审核）跑完“问题 → 检索/补查 → 后处理 → 回答 → 引用或拒答”；四题统一由真实模型依据上下文判定 `answerable/insufficient`，用作流程验收，不替代核心检索 benchmark。

先看 [C3 可选横向实验](3.%20索引阶段/比较索引增强方法.ipynb) 理解 method-fit，再看[选择一个问题](7.%20评估/选择一个问题.ipynb)和[分开检查问题、资料与回答](7.%20评估/分开检查问题、资料与回答.ipynb)，最后看[计算检索和回答指标](7.%20评估/计算检索和回答指标.ipynb)、[比较改动前后](7.%20评估/比较改动前后.ipynb)和[分析问题出在哪一步](7.%20评估/分析问题出在哪一步.ipynb)。C7 回归护栏使用同一批 6 道 canonical 问题、同一 `top_k` 和同一上下文预算，并逐题保留改善、退化与汇总；不要为每种方法复制问题集或合并不同专题的排行榜。

## 端到端 capstone 入口

完成七步主线后，运行[端到端验收 Notebook](7.%20评估/端到端验收.ipynb)，并对照[端到端验收协议](7.%20评估/端到端验收协议.md)使用少量 canonical 固定回归问题（evidence 已按固定流程审核），串起检索、信息缺口处理、后处理和回答约束。Notebook 不新增数据集，也不改写 C2 的训练范围；通过标准是每一步都有可追溯记录，且回答中的每条主要结论都能回到实际候选原文，资料不足时按规则拒答；真实权限系统需另行接入。

## 阅读和运行

建议使用 Python 3.10 的 `llm-universe-c7` kernel，并在本目录执行：

```bash
python -m pip install -r requirements-c7.txt
python scripts/check_dataset.py --dataset data/dataset
python scripts/check_tutorial.py
```

核心路径使用本地 PDF、随教程提供的向量库和本地规则，不需要付费 API。需要生成内容的页面只读取 `.env` 中的 `ZHIPUAI_API_KEY`，固定调用 `glm-4-flash`；依赖、API、资料或模型缺失时直接失败，不切换备用密钥、算法或伪造输出。重新运行前请保留 `data/`，并按 Notebook 的说明保存真实输出和来源范围。

维护者在准备最终 Git 快照时，先阅读 [`docs/维护说明.md`](docs/维护说明.md) 中的白名单，再从仓库根目录执行只读检查：`python scripts/check_c7_release_snapshot.py`。该检查只报告应纳入的 C7、`tests/c7`、根入口和 manifest 声明的完整向量库文件，不会替你暂存、提交或删除工作区文件。

多来源助手只读取 manifest 和两份当前章节 README；它不把同一份 PDF 复制成多个资料源，也不将会话回答写回 canonical 数据包。生产环境的权限、延迟、费用、稳定性和开放工具安全需要另行验证。
